# Timetable API 실험

이 코드는 근태 기록 **한 건을 읽는 서버의 초기 실험**입니다. 로그인 화면, 일반 직원 등록·권한 관리, 기록 생성·수정, QR, 사용자 화면, 운영 배포와 백업은 제공하지 않습니다. 실무에 사용할 수 있는 앱이 아닙니다.

서버는 명시적으로 설정된 기존 SQLite 데이터베이스를 읽기 전용으로 열고, 설정한 공개 키로 OAuth 접근 토큰을 검증합니다. 모든 조회에서 현재 직원 권한과 기록 소유자를 다시 확인합니다. 필수 설정이 없거나 기존 DB를 열 수 없으면 시작하지 않으며, 수신 주소는 `127.0.0.1`로 고정되어 있습니다. 이 HTTP 서버를 인터넷에 직접 노출하면 안 됩니다.

## 현재 설정 항목

| 환경 변수 | 의미 |
| --- | --- |
| `VINTAGE_ISSUER` | 신뢰할 수 있는 HTTPS 토큰 발급자 |
| `VINTAGE_AUDIENCE` | 이 API를 나타내는 토큰 대상 |
| `VINTAGE_CLIENT_ID` | 사용할 수 있도록 허용한 OAuth 클라이언트 ID |
| `VINTAGE_REQUIRED_SCOPE` | 토큰에 필요한 권한 범위 하나 |
| `VINTAGE_JWKS_FILE` | 발급자의 RSA 공개 검증 키 묶음 파일의 절대 경로 |
| `VINTAGE_DATABASE_FILE` | 초기화된 SQLite DB 파일의 절대 경로 |
| `VINTAGE_PORT` | 로컬에서 사용할 포트 번호 |

검증 키 파일에는 발급자가 제공한 공개 키만 넣어야 합니다. 서버는 키를 자동 갱신하지 않으며 토큰을 발급하거나 로그인하지 않습니다.

초기 DB를 만드는 실험 명령 `corepack pnpm --filter @vintage/timetable-api init-db`는 `VINTAGE_DATABASE_FILE`의 **아직 존재하지 않는 절대 경로**를 사용하고, 표준 입력으로 JSON의 `issuer`, `subject`, `businessId`, `staffId`를 받습니다. 각 값은 사업장 관리자가 확인해야 하며, `issuer`와 `subject`는 신뢰하는 로그인 제공자가 확인한 실제 값이어야 합니다. 새 파일에 첫 관리자 한 명을 만들며 기존 파일을 덮어쓰지 않습니다. 실패하면 불완전한 새 파일이 남을 수 있으므로 확인 없이 지우거나 다시 쓰지 않습니다. 초기화 자료와 DB에는 식별 정보가 들어가므로 저장소 밖에 두고 파일 권한을 보호해야 합니다. Windows에서는 해당 폴더와 파일의 접근 권한을 별도로 확인해야 합니다.

이 명령과 위 표는 아직 완성된 설치 안내가 아닙니다. 실제 사업장 환경에서 사용하기 전에 로그인 제공자 연결과 키 교체·토큰 취소, HTTPS, 운영 권한 관리, DB 파일 보호·마이그레이션·백업 복구와 전체 업무 흐름을 구현하고 검증해야 합니다.

테스트는 가상의 직원·사업장과 임시 데이터베이스, 메모리에서 생성한 테스트용 키만 사용합니다. `corepack pnpm --filter @vintage/timetable-api test`는 로컬 네트워크와 가상 정보로 기본 요청 경계를 시험하며 실제 로그인이나 운영 배포 검증은 아닙니다. Node.js 24의 내장 SQLite는 현재 실험적 API입니다.
