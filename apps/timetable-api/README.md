# Timetable API 실험

이 코드는 본인의 근태 기록 목록, 기록 한 건의 조회와 제한된 관리자 변경을 시험하는 **초기 API**입니다. 로그인 화면, 기존 기록의 정정·삭제, 근무 일정, QR, 사용자 화면, 운영 배포는 제공하지 않습니다. 실무에 사용할 수 있는 앱이 아닙니다.

서버는 기본적으로 명시된 기존 SQLite 데이터베이스를 읽기 전용으로 열고, 설정한 공개 키로 OAuth 접근 토큰을 검증합니다. 모든 조회에서 현재 직원 권한과 기록 소유자를 다시 확인합니다. 관리 기능은 별도 설정으로만 켜지며 별도의 토큰 권한 범위와 현재 관리자 역할을 모두 확인합니다. 필수 설정이 없거나 기존 DB를 열 수 없으면 시작하지 않으며, 수신 주소는 `127.0.0.1`로 고정되어 있습니다. 이 HTTP 서버를 인터넷에 직접 노출하면 안 됩니다.

## 현재 설정 항목

| 환경 변수 | 의미 |
| --- | --- |
| `VINTAGE_ISSUER` | 신뢰할 수 있는 HTTPS 토큰 발급자 |
| `VINTAGE_AUDIENCE` | 이 API를 나타내는 토큰 대상 |
| `VINTAGE_CLIENT_ID` | 사용할 수 있도록 허용한 OAuth 클라이언트 ID |
| `VINTAGE_REQUIRED_SCOPE` | 토큰에 필요한 권한 범위 하나 |
| `VINTAGE_JWKS_FILE` | 발급자의 RSA 공개 검증 키 묶음 파일의 절대 경로 |
| `VINTAGE_DATABASE_FILE` | 초기화된 SQLite DB 파일의 절대 경로 |
| `VINTAGE_PORT` | 로컬에서 사용할 포트 번호 |
| `VINTAGE_ENABLE_WRITES` | 생략 또는 `false`면 읽기 전용, 명시적 `true`면 관리자 변경 허용 |
| `VINTAGE_WRITE_SCOPE` | 쓰기를 켰을 때 필요한 별도의 OAuth 권한 범위. 읽기 범위와 달라야 함 |
| `VINTAGE_ENABLE_BROWSER_LOGIN` | 생략 또는 `false`면 브라우저 로그인 비활성화, 명시적 `true`면 실험 기능 활성화 |
| `VINTAGE_PUBLIC_ORIGIN` | 로그인 활성화 시 사용하는 고정 HTTPS 출처. 경로와 쿼리는 제외 |
| `VINTAGE_CLIENT_SECRET_FILE` | 로그인 활성화 시 읽을 클라이언트 비밀 파일의 절대 경로. 일반 파일이어야 함 |

검증 키 파일에는 발급자가 제공한 공개 키만 넣어야 합니다. 서버는 키를 자동 갱신하거나 토큰을 발급하지 않습니다. 로그인 제공자와의 통합은 명시적으로 켠 경우에만 시작하며, 설정된 HTTPS 발급자의 메타데이터를 읽습니다. 비밀 파일은 저장소 밖의 접근 제한된 위치에 두어야 합니다. 파일 권한은 이 프로그램이 검증하지 않으므로 운영자가 별도로 확인해야 합니다.

실험 로그인은 `GET /auth/start`, 선택적 쓰기 권한을 요청하는 `GET /auth/start-write`, `GET /auth/callback`, `POST /auth/logout`을 제공합니다. 세션은 서버 메모리에만 있으며 재시작하면 모두 사라집니다. 쿠키를 사용한 변경 요청과 로그아웃은 설정한 공개 출처의 `Origin`을 요구합니다. 서버는 로컬 HTTP만 제공하므로 실제 브라우저에서 안전하게 사용하려면 별도의 신뢰할 수 있는 HTTPS 프록시가 필요합니다. 프록시는 지정한 호스트만 허용하고 로컬 포트에 다른 사용자가 접근하지 못하게 해야 하며, `Set-Cookie` 헤더들을 각각 보존하고 인증 코드·쿠키·토큰을 로그에 기록하지 않아야 합니다. 이 배포 구성은 아직 구현하거나 검증하지 않았습니다.

## 본인 기록 목록

`GET /v1/me/history`는 인증된 사용자의 현재 활성 직원 자격과 같은 직원에게 속한 기록만 반환합니다. 관리자로 로그인해도 이 경로에서는 본인 기록만 반환합니다. `limit`은 1부터 100까지이며 생략 시 50입니다. 응답의 `nextCursor`가 `null`이 아니면 다음 요청의 `cursor`로 전달합니다. 최신 시작 시각과 기록 ID의 내림차순이며 응답에는 기록 ID와 시작·종료 시각만 포함합니다. 비활성 또는 미등록 자격은 404입니다.

커서는 암호화되지 않아 기록의 시각과 ID를 복원할 수 있습니다. 프록시 등에서 조회 URL의 쿼리를 기록하지 않도록 설정해야 합니다. 페이지를 넘기는 동안 기록이 변경되면 결과가 달라질 수 있으며, 여러 요청이 하나의 고정된 스냅샷은 아닙니다. 대량 데이터에서의 조회 성능과 운영 보존 정책은 아직 검증하지 않았습니다.

초기 DB를 만드는 실험 명령 `corepack pnpm --filter @vintage/timetable-api init-db`는 `VINTAGE_DATABASE_FILE`의 **아직 존재하지 않는 절대 경로**를 사용하고, 표준 입력으로 JSON의 `issuer`, `subject`, `businessId`, `staffId`를 받습니다. 각 값은 사업장 관리자가 확인해야 하며, `issuer`와 `subject`는 신뢰하는 로그인 제공자가 확인한 실제 값이어야 합니다. 새 파일에 첫 관리자 한 명을 만들며 기존 파일을 덮어쓰지 않습니다. 실패하면 불완전한 새 파일이 남을 수 있으므로 확인 없이 지우거나 다시 쓰지 않습니다. 초기화 자료와 DB에는 식별 정보가 들어가므로 저장소 밖에 두고 파일 권한을 보호해야 합니다. Windows에서는 해당 폴더와 파일의 접근 권한을 별도로 확인해야 합니다.

실험용 `backup-db`는 `VINTAGE_DATABASE_FILE`에서 `VINTAGE_BACKUP_FILE`로, `restore-db`는 그 반대 방향으로 복사합니다. 두 경로는 서로 다른 절대 경로여야 하고 **복사 대상은 아직 존재하지 않아야** 합니다. SQLite의 복사 기능과 무결성 검사 후 하드 링크를 지원하는 파일 시스템에 새 대상 파일을 만듭니다. 실패 시 대상 폴더에 `.vintage-copy-*` 임시 폴더가 남을 수 있습니다. 백업과 임시 폴더에도 실제 직원 정보가 그대로 들어가므로 저장소 밖의 접근이 제한된 위치에 보관하고 암호화와 별도 보관을 준비해야 합니다. Windows 파일 접근 권한은 별도로 확인해야 합니다. 복원 파일을 실제 서비스에 적용하기 전 전체 업무 흐름을 시험해야 합니다.

`migrate-db`는 기존 DB의 쓰기 잠금을 얻고 새 `VINTAGE_BACKUP_FILE`을 먼저 만든 다음 저장 구조를 변경합니다. 기존 백업을 덮어쓰지 않고, 다른 쓰기 작업이 진행 중이거나 백업에 실패하면 변경을 시작하지 않습니다. 변경 실패 시 이전 DB 상태와 이미 완성된 백업을 보존합니다.

관리 API를 켜려면 DB 구조 버전 3 이상이 필요하고, 열린 기록을 종료하려면 버전 4가 필요합니다. 새 DB는 버전 1로 시작하므로 버전 4까지는 `migrate-db`를 세 번 실행해야 하고, 매번 서로 다른 새 `VINTAGE_BACKUP_FILE` 경로가 필요합니다. 백업 파일은 각 변경 직전의 DB이며 복원은 새 파일로 시험해야 합니다.

## 실험용 관리자 API

쓰기를 명시적으로 켠 경우에만 다음 요청을 처리합니다. 인증 서버에서 발급한 Bearer 토큰은 읽기 범위와 별도 쓰기 범위를 모두 가져야 하고, DB에서 현재 활성 관리자여야 합니다. 대상 사업장은 요청 본문이 아니라 검증된 관리자의 직원 자격에서 정합니다.

| 메서드와 경로 | JSON 입력 |
| --- | --- |
| `POST /v1/admin/viewers` | `staffId`, 로그인 제공자에서 확인한 `subject` |
| `POST /v1/admin/history` | `staffId`, `recordId`, `startsAt`, `endsAt` |
| `POST /v1/admin/history/close` | `recordId`, `endsAt` |
| `POST /v1/admin/viewers/deactivate` | `staffId` |

시간은 `YYYY-MM-DDTHH:mm:ss.sssZ` UTC 형식이며, 미종료 기록의 `endsAt`은 `null`입니다. 요청은 UTF-8 JSON과 8KB 이하의 명시적 Content-Length를 사용합니다. 관리자 쓰기와 그 관리자의 직원 ID를 기록한 감사 행은 같은 DB 트랜잭션으로 저장됩니다. 다른 사업장이나 관리자 권한을 본문에 지정할 수 없으며 일반 직원은 변경할 수 없습니다.

근태 기록은 종료 시각이 시작 시각보다 늦어야 하고 같은 직원의 다른 기록과 겹칠 수 없습니다. 끝이 미정인 기록은 이후 모든 시각과 겹치며 관리자가 종료할 수 있습니다. 종료와 관리자 감사 행은 같은 트랜잭션에 기록되고, 같은 종료 시각을 다시 요청하면 중복 감사 행 없이 `replayed: true`를 반환합니다.

기록 생성 요청은 재시도할 때 같은 `recordId`와 내용을 사용해야 하며, 현재 저장된 내용이 같으면 `replayed: true`를 반환합니다. 종료 등으로 저장된 내용이 달라진 후 원래 생성 요청을 재시도하면 `409`가 반환되므로 현재 기록을 확인해야 합니다. 같은 ID로 내용이 다르거나 시간이 겹칠 때도 `409`를 반환합니다. 동시 쓰기로 DB가 잠긴 경우 `503`이 발생할 수 있으며, 재시도 시에도 같은 ID와 내용을 유지해야 합니다. 이 검사는 새로 작성하거나 종료하는 기록에 적용하며 과거 데이터가 모두 유효하다는 뜻은 아닙니다.

아직 실제 로그인 제공자와의 호환성 확인, 제공자 측 토큰 즉시 취소, 기록 정정·삭제와 추가 업무 규칙, 감사 이력 변조 방지와 운영 시 권한 관리가 구현되거나 검증되지 않았습니다. 따라서 이 API를 실제 직원 기록에 사용하면 안 됩니다.

초기 실험을 위해 `add-viewer`와 `add-history` 명령이 표준 입력 JSON으로 일반 직원 자격과 근태 기록 한 건을 각각 만듭니다. 직원 등록에는 `businessId`, `staffId`, 로그인 제공자의 `issuer`와 확인된 `subject`가 필요하고 역할은 일반 직원으로 고정됩니다. 기록 생성에는 `businessId`, `staffId`, `recordId`, `YYYY-MM-DDTHH:mm:ss.sssZ` 형식의 UTC `startsAt`과 `endsAt`(진행 중이면 `null`)이 필요합니다. `deactivate-viewer`는 `businessId`와 `staffId`로 일반 직원의 접근을 중지하며 관리자 계정에는 적용되지 않습니다. 각 변경과 감사 이력은 한 트랜잭션으로 저장됩니다. 중지된 직원은 이 API에서 다음 요청부터 거부되지만 로그인 제공자의 세션이나 토큰 자체가 취소되는 것은 아닙니다.

**이 명령은 웹 로그인이나 관리자 역할을 확인하지 않습니다.** DB 파일에 쓰기 권한이 있는 로컬 운영자가 직접 실행하는 관리 도구이므로, 해당 컴퓨터와 DB 파일의 쓰기 권한을 신뢰하는 담당자에게만 부여해야 합니다. 감사 이력에는 `local-operator`만 기록되며 실제 누가 실행했는지는 구별하지 못하고, DB 쓰기 권한자가 직접 바꿀 수도 있습니다. 운영 환경에서 쓰려면 관리자의 개인별 인증과 권한 회수·변경 이력, 변조 방지, 안전한 입력과 복구 절차를 추가로 구현하고 검증해야 합니다.

이 명령과 위 표는 아직 완성된 설치 안내가 아닙니다. 실제 사업장 환경에서 사용하기 전에 로그인 제공자 연결과 키 교체·토큰 취소, HTTPS, 운영 권한 관리, DB 파일 보호·마이그레이션·정기 백업과 복원 절차 및 전체 업무 흐름을 구현하고 검증해야 합니다.

테스트는 가상의 직원·사업장과 임시 데이터베이스, 메모리에서 생성한 테스트용 키만 사용합니다. `corepack pnpm --filter @vintage/timetable-api test`는 로컬 네트워크와 가상 정보로 기본 요청 경계를 시험하며 실제 로그인이나 운영 배포 검증은 아닙니다. Node.js 24의 내장 SQLite는 현재 실험적 API입니다.
