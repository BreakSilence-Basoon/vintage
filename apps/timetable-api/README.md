# Timetable API 실험

이 코드는 본인의 근태 기록과 예정 근무 조회, 제한된 관리자 변경을 시험하는 **초기 API**입니다. 로그인 화면, 출퇴근 기록의 정정·삭제, QR, 사용자 화면, 운영 배포는 제공하지 않습니다. 실무에 사용할 수 있는 앱이 아닙니다.

서버는 기본적으로 명시된 기존 SQLite 데이터베이스를 읽기 전용으로 열고, 설정한 공개 키로 OAuth 접근 토큰을 검증합니다. 모든 조회에서 현재 직원 권한과 기록 소유자를 다시 확인합니다. 관리 기능은 별도 설정으로만 켜지며 별도의 토큰 권한 범위와 현재 관리자 역할을 모두 확인합니다. 필수 설정이 없거나 기존 DB를 열 수 없으면 시작하지 않으며, 수신 주소는 `127.0.0.1`로 고정되어 있습니다. 이 HTTP 서버를 인터넷에 직접 노출하면 안 됩니다.

## 현재 설정 항목

| 환경 변수 | 의미 |
| --- | --- |
| `VINTAGE_ISSUER` | 신뢰할 수 있는 HTTPS 토큰 발급자 |
| `VINTAGE_AUDIENCE` | 이 API를 나타내는 토큰 대상 |
| `VINTAGE_CLIENT_ID` | 사용할 수 있도록 허용한 OAuth 클라이언트 ID |
| `VINTAGE_REQUIRED_SCOPE` | 토큰에 필요한 권한 범위 하나 |
| `VINTAGE_JWKS_FILE` | 발급자의 RSA 공개 검증 키 묶음 파일의 절대 경로 |
| `VINTAGE_DATABASE_FILE` | 초기화된 SQLite DB 파일의 절대 경로 |
| `VINTAGE_PORT` | 로컬에서 사용할 포트 번호 |
| `VINTAGE_ENABLE_WRITES` | 생략 또는 `false`면 읽기 전용, 명시적 `true`면 관리자 변경 허용 |
| `VINTAGE_WRITE_SCOPE` | 쓰기를 켰을 때 필요한 별도의 OAuth 권한 범위. 읽기 범위와 달라야 함 |
| `VINTAGE_ENABLE_BROWSER_LOGIN` | 생략 또는 `false`면 브라우저 로그인 비활성화, 명시적 `true`면 실험 기능 활성화 |
| `VINTAGE_PUBLIC_ORIGIN` | 로그인 활성화 시 사용하는 고정 HTTPS 출처. 경로와 쿼리는 제외 |
| `VINTAGE_CLIENT_SECRET_FILE` | 로그인 활성화 시 읽을 클라이언트 비밀 파일의 절대 경로. 일반 파일이어야 함 |

검증 키 파일에는 발급자가 제공한 공개 키만 넣어야 합니다. 서버는 키를 자동 갱신하거나 토큰을 발급하지 않습니다. 로그인 제공자와의 통합은 명시적으로 켠 경우에만 시작하며, 설정된 HTTPS 발급자의 메타데이터를 읽습니다. 비밀 파일은 저장소 밖의 접근 제한된 위치에 두어야 합니다. 파일 권한은 이 프로그램이 검증하지 않으므로 운영자가 별도로 확인해야 합니다.

실험 로그인은 `GET /auth/start`, 선택적 쓰기 권한을 요청하는 `GET /auth/start-write`, `GET /auth/callback`, `POST /auth/logout`을 제공합니다. 세션은 서버 메모리에만 있으며 재시작하면 모두 사라집니다. 쿠키를 사용한 변경 요청과 로그아웃은 설정한 공개 출처의 `Origin`을 요구합니다. 서버는 로컬 HTTP만 제공하므로 실제 브라우저에서 안전하게 사용하려면 별도의 신뢰할 수 있는 HTTPS 프록시가 필요합니다. 프록시는 지정한 호스트만 허용하고 로컬 포트에 다른 사용자가 접근하지 못하게 해야 하며, `Set-Cookie` 헤더들을 각각 보존하고 인증 코드·쿠키·토큰을 로그에 기록하지 않아야 합니다. 이 배포 구성은 아직 구현하거나 검증하지 않았습니다.

## 본인 기록 목록

`GET /v1/me/history`는 인증된 사용자의 현재 활성 직원 자격과 같은 직원에게 속한 기록만 반환합니다. 관리자로 로그인해도 이 경로에서는 본인 기록만 반환합니다. `limit`은 1부터 100까지이며 생략 시 50입니다. 응답의 `nextCursor`가 `null`이 아니면 다음 요청의 `cursor`로 전달합니다. 최신 시작 시각과 기록 ID의 내림차순이며 응답에는 기록 ID와 시작·종료 시각만 포함합니다. 비활성 또는 미등록 자격은 404입니다.

커서는 암호화되지 않아 기록의 시각과 ID를 복원할 수 있습니다. 프록시 등에서 조회 URL의 쿼리를 기록하지 않도록 설정해야 합니다. 페이지를 넘기는 동안 기록이 변경되면 결과가 달라질 수 있으며, 여러 요청이 하나의 고정된 스냅샷은 아닙니다. 대량 데이터에서의 조회 성능과 운영 보존 정책은 아직 검증하지 않았습니다.

초기 DB를 만드는 실험 명령 `corepack pnpm --filter @vintage/timetable-api init-db`는 `VINTAGE_DATABASE_FILE`의 **아직 존재하지 않는 절대 경로**를 사용하고, 표준 입력으로 JSON의 `issuer`, `subject`, `businessId`, `staffId`를 받습니다. 각 값은 사업장 관리자가 확인해야 하며, `issuer`와 `subject`는 신뢰하는 로그인 제공자가 확인한 실제 값이어야 합니다. 새 파일에 첫 관리자 한 명을 만들며 기존 파일을 덮어쓰지 않습니다. 실패하면 불완전한 새 파일이 남을 수 있으므로 확인 없이 지우거나 다시 쓰지 않습니다. 초기화 자료와 DB에는 식별 정보가 들어가므로 저장소 밖에 두고 파일 권한을 보호해야 합니다. Windows에서는 해당 폴더와 파일의 접근 권한을 별도로 확인해야 합니다.

실험용 `backup-db`는 `VINTAGE_DATABASE_FILE`에서 `VINTAGE_BACKUP_FILE`로, `restore-db`는 그 반대 방향으로 복사합니다. 두 경로는 서로 다른 절대 경로여야 하고 **복사 대상은 아직 존재하지 않아야** 합니다. SQLite의 복사 기능과 무결성 검사 후 하드 링크를 지원하는 파일 시스템에 새 대상 파일을 만듭니다. 독립된 복사본의 저널 모드는 DELETE로 정리하며 원본의 저널 모드는 바꾸지 않습니다. SQLite가 WAL 방식 원본 옆에 `-wal`·`-shm` 파일을 사용할 수 있으므로 사용 중인 원본의 보조 파일을 임의로 삭제하면 안 됩니다. 실패 시 대상 폴더에 `.vintage-copy-*` 임시 폴더가 남을 수 있고, 최종 파일을 만든 뒤 정리가 실패했다면 대상 파일도 이미 존재할 수 있으므로 재시도 전에 확인해야 합니다. 백업과 임시 폴더에도 실제 직원 정보가 그대로 들어가므로 저장소 밖의 접근이 제한된 위치에 보관하고 암호화와 별도 보관을 준비해야 합니다. Windows 파일 접근 권한은 별도로 확인해야 합니다. 복원 파일을 실제 서비스에 적용하기 전 전체 업무 흐름을 시험해야 합니다.

`migrate-db`는 기존 DB의 쓰기 잠금을 얻고 새 `VINTAGE_BACKUP_FILE`을 먼저 만든 다음 저장 구조를 변경합니다. 기존 백업을 덮어쓰지 않고, 다른 쓰기 작업이 진행 중이거나 백업에 실패하면 변경을 시작하지 않습니다. 변경 실패 시 이전 DB 상태와 이미 완성된 백업을 보존합니다.

관리 API를 켜려면 DB 구조 버전 3 이상이 필요하고, 열린 기록을 종료하려면 버전 4가 필요합니다. 버전 5는 본인 기록 조회 색인, 버전 6은 예정 근무 저장, 버전 7은 일정 변경 이력, 버전 8은 관리자 일정 조회 색인, 버전 9는 일정 복사 이력, 버전 10은 직원 재활성화와 토큰 발급 시각 기준, 버전 11은 내부 장소 기기 확인 실험, 버전 12는 복구 사본 준비 이력, 버전 13은 복구 중 접근 차단을 추가합니다. 새 DB는 버전 1로 시작하므로 버전 13까지는 `migrate-db`를 열두 번 실행해야 하고, 매번 서로 다른 새 `VINTAGE_BACKUP_FILE` 경로가 필요합니다. 버전 6 미만에서 예정 근무 조회·등록, 버전 7 미만에서 관리자 일정 목록과 일정 변경·취소·복구, 버전 9 미만에서 일정 복사, 버전 10 미만에서 직원 재활성화는 사용할 수 없습니다. 버전 7에서도 관리자 일정 목록은 조회할 수 있지만 버전 8 색인은 없습니다. 백업 파일은 각 변경 직전의 DB이며 복원은 새 파일로 시험해야 합니다. 버전 11의 기기 확인은 이 API에 연결되지 않았습니다.

## 실험용 관리자 API

쓰기를 명시적으로 켠 경우에만 다음 요청을 처리합니다. 인증 서버에서 발급한 Bearer 토큰은 읽기 범위와 별도 쓰기 범위를 모두 가져야 하고, DB에서 현재 활성 관리자여야 합니다. 대상 사업장은 요청 본문이 아니라 검증된 관리자의 직원 자격에서 정합니다.

| 메서드와 경로 | JSON 입력 |
| --- | --- |
| `POST /v1/admin/viewers` | `staffId`, 로그인 제공자에서 확인한 `subject` |
| `POST /v1/admin/history` | `staffId`, `recordId`, `startsAt`, `endsAt` |
| `POST /v1/admin/history/close` | `recordId`, `endsAt` |
| `POST /v1/admin/viewers/deactivate` | `staffId` |
| `POST /v1/admin/viewers/reactivate` | `staffId`, `reason` |
| `POST /v1/admin/locations` | `locationId`, `label` |
| `POST /v1/admin/shifts` | `shiftId`, `staffId`, `locationId`, `startsAt`, `endsAt`, `graceMinutes` |
| `POST /v1/admin/shifts/update` | 위 일정 입력과 `expectedRevision`, `reason` |
| `POST /v1/admin/shifts/cancel` | `shiftId`, `expectedRevision`, `reason` |
| `POST /v1/admin/shifts/restore` | `shiftId`, `expectedRevision`, `reason` |
| `POST /v1/admin/shifts/copy` | `sourceShiftId`, `sourceRevision`, 새 `shiftId`, `startsAt`, `endsAt` |

시간은 `YYYY-MM-DDTHH:mm:ss.sssZ` UTC 형식이며, 미종료 기록의 `endsAt`은 `null`입니다. 요청은 UTF-8 JSON과 8KB 이하의 명시적 Content-Length를 사용합니다. 관리자 쓰기와 그 관리자의 직원 ID를 기록한 감사 행은 같은 DB 트랜잭션으로 저장됩니다. 다른 사업장이나 관리자 권한을 본문에 지정할 수 없으며 일반 직원은 변경할 수 없습니다.

장소와 예정 근무 생성에는 버전 6이 필요합니다. 장소 이름은 앞뒤 공백이나 제어문자 없이 1~100자, 허용 지각 시간 `graceMinutes`는 0~180의 정수입니다. 이 값은 저장만 하며 아직 지각 여부를 계산하지 않습니다. 예정 근무는 현재 활성 직원과 같은 사업장 장소를 지정하고 종료가 시작보다 늦어야 하며 같은 직원의 활성 예정 근무와 겹칠 수 없습니다. 경계가 맞닿는 일정은 허용합니다. 같은 ID와 내용의 생성 재시도는 중복 저장하지 않고, 다른 내용이나 겹치는 시간은 409를 반환합니다. 변경 또는 취소된 일정의 원래 생성 요청을 다시 보내면 409입니다.

버전 7의 `GET /v1/admin/shifts/{shiftId}`는 쓰기 권한 범위를 가진 현재 관리자에게 같은 사업장의 일정과 `revision`, `active` 상태를 반환합니다. 변경·취소·복구 시 현재 `revision`과 앞뒤 공백이나 제어문자가 없는 1~500자 변경 사유를 제출해야 합니다. 다른 변경으로 버전이 달라졌거나 상태·시간이 충돌하면 409이며, 다시 조회해 확인해야 합니다. 취소된 일정은 본인 목록에서 숨겨지고 복구 시 시간 겹침을 다시 검사합니다. 생성·변경과 관리자의 감사 행은 같은 트랜잭션에서 처리하지만 감사는 DB 쓰기 권한자가 변조할 수 있습니다. 변경 사유와 전후 값에도 민감한 정보가 들어갈 수 있으므로 DB와 백업을 보호해야 합니다. 실제 출퇴근 기록과 일정 사이의 연결과 그에 따른 변경 제약은 아직 없습니다.

`GET /v1/admin/shifts`는 쓰기 권한 범위를 가진 현재 관리자가 같은 사업장 일정을 조회하는 경로입니다. `from`, `to` UTC 범위는 필수이며 최대 62일입니다. `status`는 `active`(기본), `canceled`, `all` 중 하나이고 `limit`은 1~100, 기본 50입니다. 다음 페이지에는 같은 범위와 상태를 유지하면서 응답의 `nextCursor`를 전달합니다. 결과에는 직원 ID와 장소, 시각, 버전, 취소 여부가 포함됩니다. 조회 범위와 커서는 암호화되지 않으므로 프록시 쿼리 로그에 남기면 안 되며, 페이지 간 고정 스냅샷이나 실제 대량 데이터 성능은 검증하지 않았습니다.

`GET /v1/admin/staff`는 쓰기 권한 범위를 가진 현재 관리자가 같은 사업장의 직원 ID·역할·활성 상태만 페이지로 조회합니다. `limit`은 1~100, 기본 50이며 다음 요청에는 `nextCursor`를 전달합니다. 연결된 자격이 없거나 둘 이상인 직원은 역할을 표시하지 않고 `needs_review`로 반환하며 자동 재활성화하지 않습니다. 로그인 제공자의 사용자 식별자는 이 목록에 반환하지 않습니다. 직원 ID와 커서는 민감할 수 있어 로그에 남기면 안 됩니다.

직원 재활성화는 버전 10에서 자격이 정확히 하나인 비활성 일반 직원에게만 적용되며, 사유와 관리자 감사가 같은 트랜잭션에 저장됩니다. 이미 활성 상태이거나 대상이 모호하면 409입니다. 재활성화 시 이전 토큰은 거부하고 다음 초 이후 발급된 토큰을 요구하므로 직원은 다시 로그인해야 할 수 있습니다. 이는 이 API의 접근 제어이며 로그인 제공자의 토큰 자체를 취소하지 않습니다. 서버와 제공자의 시계가 정확해야 합니다. 과거 DB 백업의 일반 복원은 이 기준도 이전 상태로 되돌립니다.

## 오프라인 복구 사본 준비

일반 `restore-db`는 원래 상태의 사본을 만들므로 예전 토큰 기준, 기기 자격과 확인 값도 되살아날 수 있습니다. 실험용 `prepare-restored-db`는 버전 11~13 백업의 절대 경로를 `VINTAGE_BACKUP_FILE`로, 아직 없는 새 파일의 절대 경로를 `VINTAGE_PREPARED_RESTORE_FILE`로 받아 별도 사본을 준비합니다. 원본과 기존 파일을 변경하지 않고, 모든 직원 자격을 비활성화하고 이전 토큰 기준을 갱신하며 모든 기기를 폐기하고 미사용 확인 값을 무효화합니다. 복구 확인이 끝나기 전에는 서비스가 시작되지 않습니다. 백업에 활성 관리자 후보가 없거나 이전 복구가 아직 확인 중이면 사본을 게시하지 않습니다. 변경 전 백업을 대신하지 않으며 서비스에 사본을 자동 적용하지도 않습니다.

담당자는 현재 권한 정본과 로그인 제공자의 실제 신원을 먼저 대조해야 합니다. 그 후 `recover-admin`은 `VINTAGE_PREPARED_RESTORE_FILE`로 준비된 사본을 지정하고 표준 입력 JSON으로 확인된 관리자의 `issuer`, `subject`, `reason`을 받아, 백업 당시 활성 관리자였던 후보 한 명만 활성화합니다. 복구 후보의 발급자와 사용자 식별자는 사본 DB에 저장되므로 DB와 백업의 접근을 제한해야 합니다. 이 명령은 그 신원이 지금도 정당한지 자동으로 확인하지 않으며, 확인과 입력은 신뢰된 로컬 담당자의 책임입니다. 나머지 직원은 비활성 상태로 남고 관리자가 현재 권한을 확인한 뒤 재활성화해야 합니다. 복구 명령이 실패했거나 결과를 확인할 수 없다면 사본을 검사한 뒤 조치해야 합니다.

로그인 제공자 측 세션·토큰 철회, 다른 관리자 권한 복구, 기기 비밀의 안전한 재발급, 서버·제공자 시계 확인과 실제 복구 절차는 별도로 준비하고 검증해야 합니다. 기기는 새 ID로 다시 등록해야 합니다. 복구와 확인 기록은 `local-operator`로 남으며 DB 쓰기 권한자가 수정할 수 있습니다. 도구는 로컬 담당자나 DB 쓰기 권한자가 직접 권한을 바꾸는 것을 막지 않습니다.

대상 폴더는 하드 링크를 지원하고 접근이 제한되어야 합니다. 실패 또는 정리 실패 시 민감한 `.vintage-restore-*`나 `.vintage-copy-*` 폴더가 남을 수 있어 보호된 위치에서 확인해야 합니다. Windows 파일 권한은 도구가 보장하지 않습니다. 이 절차는 가상 자료로만 검증했으며 실제 복구에 바로 사용할 수 있는 운영 절차가 아닙니다.

일정 복사는 같은 사업장의 활성 원본과 현재 `sourceRevision`을 확인하고 직원·장소·허용 지각 시간을 복사합니다. 새 시각과 ID는 요청에서 지정하고, 활성 직원 자격과 시간 겹침을 다시 검사합니다. 복사와 원본 버전·당시 값 및 관리자 감사는 같은 트랜잭션에 저장됩니다. 같은 요청의 재시도는 대상이 그대로면 중복 저장하지 않으며, 대상이 변경·취소되었거나 다른 요청과 충돌하면 409입니다. 복사 이력에도 직원 정보가 포함되므로 DB와 백업을 보호해야 합니다.

`GET /v1/me/shifts`는 `from`과 `to` UTC 시각을 요구하며, `[from, to)`에 겹치는 본인 일정만 조회합니다. 최대 기간은 62일이며 `limit`은 1~100, 기본 50입니다. `nextCursor`를 다음 요청에 전달하면 이어서 조회할 수 있습니다. 커서는 암호화되지 않으므로 프록시 쿼리 로그에 남기면 안 됩니다. 페이지 간 고정 스냅샷은 제공하지 않습니다.

근태 기록은 종료 시각이 시작 시각보다 늦어야 하고 같은 직원의 다른 기록과 겹칠 수 없습니다. 끝이 미정인 기록은 이후 모든 시각과 겹치며 관리자가 종료할 수 있습니다. 종료와 관리자 감사 행은 같은 트랜잭션에 기록되고, 같은 종료 시각을 다시 요청하면 중복 감사 행 없이 `replayed: true`를 반환합니다.

기록 생성 요청은 재시도할 때 같은 `recordId`와 내용을 사용해야 하며, 현재 저장된 내용이 같으면 `replayed: true`를 반환합니다. 종료 등으로 저장된 내용이 달라진 후 원래 생성 요청을 재시도하면 `409`가 반환되므로 현재 기록을 확인해야 합니다. 같은 ID로 내용이 다르거나 시간이 겹칠 때도 `409`를 반환합니다. 동시 쓰기로 DB가 잠긴 경우 `503`이 발생할 수 있으며, 재시도 시에도 같은 ID와 내용을 유지해야 합니다. 이 검사는 새로 작성하거나 종료하는 기록에 적용하며 과거 데이터가 모두 유효하다는 뜻은 아닙니다.

아직 실제 로그인 제공자와의 호환성 확인, 제공자 측 토큰 즉시 취소, 기록 정정·삭제와 추가 업무 규칙, 감사 이력 변조 방지와 운영 시 권한 관리가 구현되거나 검증되지 않았습니다. 따라서 이 API를 실제 직원 기록에 사용하면 안 됩니다.

초기 실험을 위해 `add-viewer`와 `add-history` 명령이 표준 입력 JSON으로 일반 직원 자격과 근태 기록 한 건을 각각 만듭니다. 직원 등록에는 `businessId`, `staffId`, 로그인 제공자의 `issuer`와 확인된 `subject`가 필요하고 역할은 일반 직원으로 고정됩니다. 기록 생성에는 `businessId`, `staffId`, `recordId`, `YYYY-MM-DDTHH:mm:ss.sssZ` 형식의 UTC `startsAt`과 `endsAt`(진행 중이면 `null`)이 필요합니다. `deactivate-viewer`는 `businessId`와 `staffId`로 일반 직원의 접근을 중지하며 관리자 계정에는 적용되지 않습니다. 각 변경과 감사 이력은 한 트랜잭션으로 저장됩니다. 중지된 직원은 이 API에서 다음 요청부터 거부되지만 로그인 제공자의 세션이나 토큰 자체가 취소되는 것은 아닙니다.

**이 명령은 웹 로그인이나 관리자 역할을 확인하지 않습니다.** DB 파일에 쓰기 권한이 있는 로컬 운영자가 직접 실행하는 관리 도구이므로, 해당 컴퓨터와 DB 파일의 쓰기 권한을 신뢰하는 담당자에게만 부여해야 합니다. 감사 이력에는 `local-operator`만 기록되며 실제 누가 실행했는지는 구별하지 못하고, DB 쓰기 권한자가 직접 바꿀 수도 있습니다. 운영 환경에서 쓰려면 관리자의 개인별 인증과 권한 회수·변경 이력, 변조 방지, 안전한 입력과 복구 절차를 추가로 구현하고 검증해야 합니다.

이 명령과 위 표는 아직 완성된 설치 안내가 아닙니다. 실제 사업장 환경에서 사용하기 전에 로그인 제공자 연결과 키 교체·토큰 취소, HTTPS, 운영 권한 관리, DB 파일 보호·마이그레이션·정기 백업과 복원 절차 및 전체 업무 흐름을 구현하고 검증해야 합니다.

테스트는 가상의 직원·사업장과 임시 데이터베이스, 메모리에서 생성한 테스트용 키만 사용합니다. `corepack pnpm --filter @vintage/timetable-api test`는 로컬 네트워크와 가상 정보로 기본 요청 경계를 시험하며 실제 로그인이나 운영 배포 검증은 아닙니다. Node.js 24의 내장 SQLite는 현재 실험적 API입니다.
