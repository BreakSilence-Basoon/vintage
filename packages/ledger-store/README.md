# Ledger 저장 실험

이 패키지는 별도 SQLite 데이터베이스에 실험용 사실을 저장하고 정정 전후 내용을 함께 기록하는 **신뢰된 서버 내부 구성 요소**입니다. 선택적인 토큰·권한 검사 실험은 있지만 네트워크 경로가 없고 실제 운영 인증을 검증하지 않았습니다. 한 데이터베이스를 한 설치의 경계로 취급할 뿐 사업장 간 격리를 검증하지 않았습니다. 실제 거래 자료를 넣거나 업무에 사용하면 안 됩니다.

초기화는 비어 있는 DB에만 허용하며 기존 테이블을 덮어쓰지 않습니다. 생성은 예상 버전 0, 정정은 읽은 현재 버전을 제출합니다. 새 기록과 변경 전후 내용, 호출자가 제공한 작업자 ID를 한 트랜잭션에 저장합니다. 같은 작업 ID·작업자·예상 버전·내용을 다시 제출하면 원래 처리 결과를 돌려주고, 같은 작업 ID를 다른 내용으로 재사용하거나 다른 정정으로 버전이 바뀐 경우 거부합니다. 같은 사실을 서로 다른 ID로 제출하는 중복은 찾지 못합니다. 오류나 응답 유실만으로 저장 여부를 단정하지 말고 동일한 작업 ID와 내용을 유지해 확인해야 합니다. SQLite 잠금 중에는 요청이 실패할 수 있으며 성공이 보장되지는 않습니다.

기본 함수의 작업자 ID는 호출자가 입력한 값일 뿐 신원을 인증하지 않습니다. DB 쓰기 권한자는 변경 이력을 수정할 수 있어 변조 방지 감사가 아닙니다. DB와 로그·백업에는 민감한 금액과 식별자가 포함될 수 있으며 운영 접근권한·암호화는 아직 구현하거나 검증하지 않았습니다.

## 선택적 권한 실험

신뢰된 로컬 담당자가 서비스를 멈춘 상태에서 `initializeLedgerAuthority`로 사업장 ID를 설정하면 기본 권한 없이 시작합니다. `setLedgerGrant`로 명시적으로 승인한 사용자만 접근할 수 있으며, 이 로컬 함수는 담당자를 인증하거나 권한의 타당성을 판단하지 않습니다. 현재 실험에서는 작업자 ID 하나를 발급자·사용자 식별자 한 쌍에만 연결할 수 있습니다. 권한 부여·변경 전후와 담당자 입력은 DB에 기록되지만 DB 쓰기 권한자는 수정할 수 있습니다. 비활성 사용자 재활성화나 읽기·쓰기 권한 재부여 시 이전 토큰이 다시 사용되지 않도록 새 발급 기준을 현재 시각보다 나중으로 지정해야 합니다. 서버와 발급자의 시계가 정확해야 합니다.

`createLedgerAuthorizedStore`는 설정된 서명 키로 토큰을 검증하고 같은 DB의 현재 권한을 조회합니다. 실제 쓰기와 재시도는 쓰기 잠금을 얻은 트랜잭션 안에서 권한을 다시 확인한 뒤 처리합니다. 권한 회수가 먼저 커밋됐다면 이후 쓰기는 거부되고, 쓰기가 먼저 잠금을 잡았다면 회수는 쓰기가 끝난 뒤 진행하거나 잠금 오류가 납니다. 읽기 역시 읽기 트랜잭션에서 권한과 기록을 확인하지만 이미 시작된 읽기는 회수 전 스냅샷을 볼 수 있습니다. 권한을 설정한 DB에서는 기존의 인증 없는 기본 읽기·쓰기 함수가 거부됩니다.

이 실험의 명시적 읽기·쓰기 권한은 **해당 DB 전체 기록**에 적용되며 기록별 소유자·직원·역할 구분은 없습니다. 이 범위가 실제 사업장 정책에 적합한지 정해지지 않았으므로 실제 사용자에게 적용하면 안 됩니다. 신뢰된 내부 코드에 대한 실험으로, DB에 직접 접근하거나 구버전 코드를 실행하는 사람을 막지 못합니다. 서버의 키 설정·로컬 권한 변경·DB 파일을 신뢰할 수 있어야 합니다. 실제 인증 제공자 연결과 토큰 철회·키 교체, 권한 위임 정책, 접근권한·암호화·배포 및 실사용은 미완료이며 API를 제공하지 않습니다. 복구 준비 사본은 저장된 사용자를 모두 비활성화합니다. 담당자가 백업 이후 변경과 현재 권한을 별도 정본에서 확인하지 않으면 이전 권한을 재활성화하면 안 됩니다. 일반 복사나 구버전으로 복구하면 이 보호가 자동 적용되지 않습니다.

## 실험용 백업과 복원 사본

`@vintage/ledger-store/backup`의 `copyLedgerDatabase`는 SQLite 백업 기능을 이용해 기존 DB에서 아직 없는 새 절대 경로로 사본을 만듭니다. 복사본의 SQLite 무결성·외래 키, 버전과 필수 테이블·열을 확인한 뒤 하드 링크를 지원하는 파일 시스템에서 새 파일로 게시합니다. 동일한 함수로 백업에서 다른 새 파일에 복원 사본을 만들 수 있습니다. 기존 파일은 덮어쓰지 않으며 원본이나 서비스에 사본을 자동 적용하지 않습니다. 이 검사는 데이터가 정확한 실제 거래인지, 전체 스키마가 위조되지 않았는지, 감사 내용이 변조되지 않았는지를 확인하지 않습니다.

백업은 특정 시점의 사본입니다. 그 뒤에 기록된 거래나 작업 ID는 포함되지 않으므로 과거 사본을 사용하면 최신 변경이 빠지고 이미 처리한 요청을 새 요청으로 볼 수 있습니다. 복구 적용 전 최신 기록과 외부 작업 여부를 사람이 대조해야 하며, 이런 대조·권한 복구·실제 운영 복구는 아직 구현하거나 시험하지 않았습니다. 이 사본을 실제 거래 업무에 사용하지 마세요.

`@vintage/ledger-store/recovery`의 `prepareLedgerRecovery`는 기존 백업을 변경하지 않고 새 오프라인 사본을 준비하며, 일반 기록 생성·정정과 같은 요청 재시도를 모두 차단합니다. 신뢰된 로컬 담당자는 사본을 읽어 검토할 수 있습니다. 담당자가 백업 이후의 기록과 외부에서 처리한 요청을 최신 정본과 직접 대조한 다음 `unlockLedgerRecovery`에 확인 여부, 작업자 ID와 이유를 명시하면 차단이 해제되고 확인 기록이 저장됩니다. 이 값은 담당자의 **수동 확인 표시**일 뿐 도구가 실제 대조, 누락 복구 또는 작업자 신원을 검증하지 않습니다. DB 쓰기 권한자는 차단과 확인 기록을 변경할 수 있습니다. 사본 자동 적용, 실제 운영 복구와 인증 제공자의 권한 확인은 제공하지 않습니다.

`compareLedgerRecovery`는 확인 대기 중인 복구 사본과 담당자가 지정한 별도 기준 DB를 읽기 전용으로 비교합니다. 사실과 작업 기록 각각에 대해 사본에만 있는 수, 기준에만 있는 수, 같은 ID의 내용이 다른 수, 같은 수를 반환하며 ID나 금액은 반환하지 않습니다. **사용자 권한이나 권한 변경 이력은 비교하지 않습니다.** 기준 파일이 최신이고 같은 사업장의 정본인지 도구는 확인하지 못합니다. 두 DB의 읽기 시점도 완전히 동시에 고정되지 않으므로 쓰기 작업을 중지한 오프라인 사본으로 비교해야 합니다. 각 건의 상세 검토, 외부 서비스의 처리 내역 확인과 빠진 기록의 복원은 제공하지 않습니다. 차이가 0이어도 모든 거래가 존재하거나 정확하다는 뜻이 아니며, 비교 결과가 복구 잠금을 자동으로 해제하지도 않습니다. 현재 수동 해제는 이 비교를 강제하지 않습니다.

이 비교 함수는 인증·인가를 수행하지 않으며 집계 결과도 민감할 수 있습니다. 신뢰된 로컬 담당자만 호출해야 하고 파일이나 결과를 외부에 공개해서는 안 됩니다. 운영 접근 경계에는 현재 사용자 확인, 사업장별 권한 검증, 접근 철회, 파일 보호와 로그·백업 보호가 별도로 필요합니다. 이를 구현하거나 실제 인증 제공자와 시험하기 전에는 API로 노출하지 않습니다.

기본 `copyLedgerDatabase`는 백업의 상태를 그대로 복사하는 기능이므로 별도의 복구 차단을 추가하지 않습니다. 특히 기존 버전 1 백업을 그대로 복사한 사본은 잠겨 있지 않습니다. 안전한 복구 실험에는 위 준비 기능을 사용해야 하며, 이전 버전의 코드나 DB 직접 수정은 이 차단을 지킬 수 없습니다. 준비된 사본의 백업은 잠금 상태를 유지하고, 확인이 끝난 사본에서 다시 복구용 사본을 만들면 새 확인이 필요합니다.

DB·백업과 대상 폴더의 접근권한, 암호화 및 별도 보관은 호출자의 책임입니다. 파일 생성 모드만으로 Windows 접근권한은 보장하지 않습니다. 실패하면 대상 폴더에 `.ledger-copy-*` 또는 `.ledger-recovery-*` 임시 폴더가 남을 수 있으며, 사본 게시 이후 정리가 실패했다면 대상 파일도 이미 존재할 수 있습니다. 이 파일과 폴더에도 민감한 기록이 들어갈 수 있으므로 삭제하거나 재시도하기 전에 확인해야 합니다. 사용 중인 원본의 `-wal`·`-shm` 파일은 임의로 지우지 않습니다. 테스트는 가상 자료만 사용합니다.

통화의 실제 유효성·단위, 증빙과 사실의 연결, 직원과 정산 관계, 보존·정정 사유, 삭제, 세금·합계·환율 등은 정하지 않았습니다. 입력은 실제 사실로 검증되지 않으며 문서·결제·정산을 서로 추론하지 않습니다. 현재 Node.js의 `node:sqlite`는 실험적 기능입니다.

트랜잭션은 [SQLite 문서](https://www.sqlite.org/lang_transaction.html), 접근 제어의 필요성은 [OWASP 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)을 참고했습니다. 이는 운영 보안이나 표준 인증을 의미하지 않습니다.
