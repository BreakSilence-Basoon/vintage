# Timetable 저장소 준비

직원 자격과 출퇴근 기록을 사업장 범위로 조회하기 위한 실험적 SQLite 저장소입니다. 이 패키지만으로 앱을 설치하거나 운영할 수는 없습니다. 테이블 초기화는 명시적으로 호출하며, 조회가 DB를 새로 만들거나 초기화하지 않습니다.

사업장과 직원의 관계를 외래 키로 확인하고, 직원 자격은 발급자와 주체를 함께 조회합니다. 출퇴근 기록은 사업장과 기록 ID를 함께 조회합니다. 데이터베이스 연결과 파일 위치·권한·암호화·백업은 호출자가 책임집니다. 로그인, 웹 기반 사용자·권한 관리와 기록 수정, 보존 기간은 아직 구현되지 않았습니다.

테스트에는 임시 파일과 가상 자료만 사용합니다. 운영에 쓰기 전에는 실제 로그인·서버 통합, 데이터 이전·마이그레이션, 동시성, 무결성, 백업·복구, 저장소 보호 및 실사용 검증이 필요합니다. `node:sqlite`는 Node.js 버전별 제공 상태를 확인해야 합니다.

실험용 DB 복사는 SQLite 백업 기능을 사용하고 임시 복사본의 무결성과 외래 키를 검사한 뒤 새 대상 파일을 만듭니다. 기존 파일을 덮어쓰지 않으며 대상 파일 시스템은 하드 링크를 지원해야 합니다. 복사 실패 시 대상 폴더에 `.vintage-copy-*` 임시 폴더가 남을 수 있고 이 폴더에도 민감한 데이터가 있을 수 있습니다. 무결성 통과는 실제 서비스 복구까지 검증됐다는 뜻이 아닙니다.

로컬 관리 명령은 새 일반 직원과 기록을 추가하거나 일반 직원 접근을 중지하고 같은 트랜잭션에 감사 행을 남깁니다. 이 명령은 DB 파일 쓰기 권한이 있는 로컬 운영자를 신뢰하며 웹 로그인 권한을 검증하지 않습니다. 감사에는 운영자 유형만 남으므로 개인별 책임 추적은 아직 지원하지 않습니다.

버전 3에서는 검증된 토큰의 주체를 현재 직원 명부와 대조해 활성 관리자일 때만 자신의 사업장 데이터를 변경하고, 같은 트랜잭션에 관리자 직원 ID를 기록합니다. 이 기록도 DB 쓰기 권한자가 직접 변경할 수 있으므로 변조 방지 감사 시스템은 아닙니다. 로그인 제공자 연결과 운영 검증 전에는 사용하지 않습니다.

새 근태 기록은 같은 직원의 시간과 겹치지 않도록 쓰기 트랜잭션 안에서 확인합니다. API가 현재 저장된 내용과 같은 ID·내용으로 생성을 재시도하면 기존 결과로 처리하고 감사 행을 중복 생성하지 않습니다. 관리자는 버전 4에서 열린 기록을 종료할 수 있습니다. 기존 데이터의 중복을 자동 수정하거나 종료된 기록을 정정하지는 않습니다.
# 장소 기기 확인 실험

DB 버전 11의 `@vintage/timetable-store/kiosk`는 신뢰된 서버 코드가 장소 기기를 등록·폐기하고 짧은 수명의 일회용 확인 값을 시험하는 내부 구성 요소입니다. 기기 비밀과 확인 값은 각각 무작위 32바이트이며 DB에는 SHA-256 해시만 저장합니다. 확인은 현재 활성 직원과 같은 사업장·활성 기기·요청 종류·만료·미사용 상태를 하나의 쓰기 트랜잭션에서 검사합니다. 기기 폐기 후에는 발급된 확인 값도 거부합니다. 기기별 유효 미사용 확인 값은 최대 64개이며 유효 기간은 호출자가 1~300초로 명시합니다.

이 구성 요소는 아직 HTTP 경로, 실제 QR 생성·카메라에 연결되지 않았습니다. 버전 14의 내부 예정 근무 출퇴근 실험만 확인 값 사용과 기록·감사를 같은 트랜잭션으로 연결합니다. 호출자는 토큰 서명과 권한 범위를 먼저 검증해야 합니다. 확인 시 실행하는 `action`은 요청에서 받은 코드가 아니라 검토된 서버 코드여야 하며, 동기 함수로 같은 DB 트랜잭션 안에서만 작업해야 합니다. 자체 커밋·롤백, 외부 부작용, 비동기 작업을 시작하면 안 됩니다. 비동기 함수나 Promise 반환은 거부하지만 일반 함수의 자체 커밋이나 비동기 작업까지 방지하지는 못합니다. 이를 지키지 않으면 원자성을 보장할 수 없습니다.

등록 시 기기 비밀은 한 번만 반환되므로 보호된 전달·저장 절차가 필요합니다. 비밀·확인 값은 로그, URL, 명령줄 인자 또는 공개 저장소에 남기면 안 됩니다. 발급 후 저장된 확인 값은 자동으로 삭제되지 않으며 보존 및 정리 정책은 아직 없습니다. 서버 시계가 정확해야 하고, QR을 제3자가 전달하거나 중계할 가능성도 있어 이 방식만으로 물리적 위치를 증명할 수 없습니다.

이전 DB 백업의 일반 복원은 폐기한 기기나 사용한 확인 값을 되살릴 수 있습니다. 버전 11 이상 백업에서 별도의 오프라인 복구 사본을 준비하는 실험 도구는 모든 직원 접근을 막고 기존 토큰 기준을 갱신하며 기기·미사용 확인 값을 무효화합니다. 서비스 시작은 로컬 담당자가 현재 권한을 직접 확인해 관리자 한 명을 복구할 때까지 차단되며, 로그인 제공자의 세션이나 선택한 관리자의 현재 권한을 도구가 자동 확인하지는 않습니다. 새 기기 비밀의 안전한 발급, 나머지 직원의 현재 권한 대조, 기기 탈취 대응, 요청 제한, TLS·배포 구성과 실제 사용자 확인도 미완료이므로 실제 출퇴근에 사용하면 안 됩니다. 재사용 방지와 트랜잭션 설계는 [NIST 재사용 방지](https://pages.nist.gov/800-63-4/sp800-63b.html), [OWASP 거래 승인](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html), [SQLite 트랜잭션](https://www.sqlite.org/lang_transaction.html)을 참고했으며 표준 인증을 의미하지 않습니다.

## 예정 근무 출퇴근 내부 실험

`@vintage/timetable-store/scheduled-clock`은 검증된 사용자와 서버가 지정한 허용 시간 범위를 신뢰된 입력으로 받습니다. 현재 활성 직원·예정 근무 버전·기기 장소·일회용 확인 값과 서버 시각을 확인하고, 출근 또는 퇴근 기록·감사·확인 값 사용을 함께 저장합니다. 퇴근은 출근에 사용한 동일 기기여야 합니다. 기록이 연결된 일정의 변경·취소와 연결된 출퇴근 기록의 관리자 종료는 현재 거부합니다. 허용 시간 범위에는 기본값이 없으며 설치자가 정해야 합니다. 이 함수가 인증 토큰이나 권한 범위를 직접 검증하지는 않습니다.

아직 HTTP 출퇴근 경로, 실제 기기 등록·비밀 전달, 화면, 무예정 근무, 기록 정정·삭제, 지각 계산은 없습니다. 복구 사본에서는 기존 기기를 모두 폐기하므로 진행 중인 출근 기록을 같은 기기로 퇴근 처리할 수 없고, 이 상황을 해결할 정정 절차도 아직 없습니다. 실제 직원 기록에 사용하지 마세요.

서버 전용 `getScheduledAttendanceReceipt`는 동일한 확인 값·행위·일정 버전과 현재 활성 직원 자격으로 이미 확정된 원래 결과를 조회합니다. 확인 값은 만료 후에도 같은 직원의 영수증 조회에 필요하며 로그나 URL에 남기면 안 됩니다. 출근 영수증은 이후 퇴근하더라도 원래 출근 결과를 반환합니다. 다른 직원, 다른 사업장, 중지된 자격, 다른 요청은 결과를 받지 못합니다. 조회 결과가 없다고 원래 요청이 실패했거나 진행 중이 아니라고 판단할 수 없습니다. 같은 확인 값으로 원래 요청을 재시도하면 중복 기록 없이 이미 사용된 값은 거부되므로, 호출자는 거부 뒤에도 영수증을 재조회해야 합니다. 원래 확인 값을 분실했거나 이전 백업으로 복원한 경우에는 결과를 자동 확정할 수 없습니다. 이 경로는 서버 내부 실험이며 네트워크 응답 유실·인증 전달·클라이언트 재시도나 데이터 보존 정책을 아직 구현하거나 실사용 검증하지 않았습니다.

실제 API DB 연결의 SQLite 잠금 대기 시간은 현재 0초입니다. 다른 연결이 쓰기 잠금을 잡은 시험에서 관리자 쓰기는 `503 unavailable`을 반환했고, 내부 출퇴근 함수는 구체적 원인을 숨긴 일반 오류를 반환했습니다. 이 시험에서 트랜잭션 시작 전에 잠금이 거부되었을 때는 기록과 확인 값이 바뀌지 않아 잠금 해제 후 같은 확인 값으로 진행할 수 있었습니다. 일반 오류나 응답 유실만으로 그 상황이라고 단정할 수 없습니다. 내부 출퇴근 함수에는 아직 HTTP 응답이 없습니다.

별도 시험에서는 DELETE 저널 모드에서 다른 연결이 읽기 트랜잭션을 유지하는 동안 쓰기 시작은 성공했지만 `COMMIT`이 SQLite 오류 코드 5로 실패했습니다. 내부 출퇴근의 기록·감사·확인 값 사용은 함께 롤백되었고 읽기 잠금 해제 후 같은 확인 값으로 진행할 수 있었습니다. 기존 관리자 HTTP도 이 조건에서 503을 반환하고 변경을 롤백했습니다. 이는 두 요청이 모두 거절된 이전 시험의 원인을 증명하지 않으며 WAL 모드나 실제 운영 환경의 모든 잠금 상황을 검증한 것은 아닙니다.

가상 DB에서 대기 시간 0초로 별도 프로세스의 요청 20쌍을 시험한 한 실행에서는 14쌍이 `BEGIN IMMEDIATE` 잠금 오류와 성공, 5쌍이 일반 거부와 성공, 1쌍이 `BEGIN IMMEDIATE`와 `COMMIT`의 잠금 오류로 모두 거부됐습니다. 두 잠금 오류의 SQLite 코드는 5였습니다. 이 결과는 이전 실패의 원인이나 운영 성공률을 증명하지 않습니다.

동시성 시험은 별도 연결에서 대기 시간 2초를 설정해 한 요청만 성공하는 경우와, 실제 설정과 같은 0초에서 성공이 0건 또는 1건일 수 있음을 각각 검사합니다. 두 방식 모두 중복 기록이 없어야 하며, 0건이면 상태 확인 후 재시도도 시험합니다. 과거 한 시험에서 두 요청이 모두 일반 오류로 거부된 정확한 원인은 확인하지 못했습니다. 2초를 기다린 시험의 성공을 실제 서버의 성공 보장으로 해석하면 안 됩니다. 현재 SQLite 연결은 동기 방식이므로 실제 대기 시간을 늘리면 다른 요청도 지연될 수 있으며, 운영 설정을 바꾸기 전 별도 부하 검증이 필요합니다. 실제 환경의 동시성·지연과 복구 절차는 검증하지 않았습니다.
